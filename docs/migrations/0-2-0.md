# Migration notes for 0.2.0

## Qdrant Quadlet observer parameters

The Qdrant Quadlet validation entry points now accept observer trait objects:

```rust
pub fn validate_checked_in_qdrant_quadlet(
    observer: &dyn QdrantQuadletObserver,
) -> Result<(), QdrantQuadletError>;

pub fn validate_qdrant_quadlet(
    contents: &str,
    observer: &dyn QdrantQuadletObserver,
) -> Result<(), QdrantQuadletError>;
```

Existing callers that pass a concrete observer by reference do not need to
change:

```rust
validate_qdrant_quadlet(contents, &TracingQdrantQuadletObserver)?;
```

Callers that store observers behind trait objects can now pass those references
directly:

```rust
let observer: &dyn QdrantQuadletObserver = &TracingQdrantQuadletObserver;
validate_qdrant_quadlet(contents, observer)?;
```

Tests that do not need telemetry can continue to pass `&()` because `()`
implements `QdrantQuadletObserver` as a no-op observer.

## Repovec system user and directory layout (roadmap 1.3.3)

The appliance now provisions the `repovec` system user and its directory tree
through a dedicated oneshot, `repovec-provision.service`, backed by two
checked-in assets:

- `packaging/sysusers.d/repovec.conf` creates the `repovec` account with the
  nologin shell and the `/var/lib/repovec` home.
- `packaging/tmpfiles.d/repovec.conf` creates the data tree with mode `0700`
  owned by `repovec` and `qdrant-storage` with mode `0700` owned `root:root`.
  It deliberately does not declare `/etc/repovec`: that directory has exactly
  one provisioning authority, the `repovec-qdrant-api-key` helper, which
  creates it as `0750 root:repovec` and rejects any `tmpfiles.d` entry for it.

### Operator actions

An existing installation must install the new assets and reload systemd before
restarting the target:

```sh
install -D -m 0644 packaging/systemd/repovec-provision.service \
    /etc/systemd/system/repovec-provision.service
install -D -m 0644 packaging/systemd/repovec.target \
    /etc/systemd/system/repovec.target
install -D -m 0644 packaging/systemd/repovecd.service \
    /etc/systemd/system/repovecd.service
install -D -m 0644 packaging/systemd/repovec-mcpd.service \
    /etc/systemd/system/repovec-mcpd.service
install -D -m 0644 packaging/systemd/repovec-qdrant-api-key.service \
    /etc/systemd/system/repovec-qdrant-api-key.service
install -D -m 0644 packaging/systemd/qdrant.container \
    /etc/containers/systemd/qdrant.container
install -D -m 0644 packaging/sysusers.d/repovec.conf \
    /usr/lib/sysusers.d/repovec.conf
install -D -m 0644 packaging/tmpfiles.d/repovec.conf \
    /usr/lib/tmpfiles.d/repovec.conf
systemctl daemon-reload
systemctl restart repovec.target
```

`repovec.target` pulls in `repovec-provision.service`, so a target restart is
enough to create the account and tree. The oneshot returns to inactive after a
successful run, so restarting the target again re-applies the idempotent
declarations after an asset update or directory drift. Every consuming unit
declares `Requires=repovec-provision.service`, so a failed provisioning run
cancels the dependent jobs instead of leaving them running against a
half-provisioned host. Operators can also re-run only the provisioning unit with
`systemctl restart repovec-provision.service`; systemd restarts active
consumers that require it.

### Fail-closed startup

`repovecd` and `repovec-mcpd` now run a live layout pre-flight during startup,
before the Qdrant probe. Startup aborts with exit status 1 and an
`error_category` log field when any required directory is missing, is not a
directory, cannot be inspected, or carries the wrong owner, group, or mode. The
check also rejects a pre-existing `repovec` account that `systemd-sysusers`
would not repair: a root uid, a home other than `/var/lib/repovec`, or a shell
other than `/usr/sbin/nologin`.

Hosts that already carry a `repovec` account should inspect it before upgrading:

```sh
getent passwd repovec
getent group repovec
```

A wrong uid, home, or shell must be repaired by hand, because
`systemd-sysusers` leaves an existing account untouched.
